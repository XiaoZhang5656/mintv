# 全 Java + 低性能 TV 播放器：选型定论

## 结论一句话
UI 用 **纯 Java 原生 View + 自定义 onDraw（零外部依赖）**，播放用 **Media3 ExoPlayer 的 Java 壳（androidx.media3 只有极少量 Kotlin 内部代码，对你写的代码无影响）**。
真正“全 Java 零 Kotlin”的备选是 `android.media.MediaPlayer` + `VideoView`，但它撑不住 HLS 切流/断线重连/软解，不建议做主线。

## 为什么“全 Java”这个约束本身不是问题
- Android 平台 API（View、Canvas、Paint、RecyclerView、Presenter、Accessibility）本来就是 Java API。
- 你在 TV 上看到的“漂亮流畅”体验，瓶颈不是语言，是**这四件事**：
  1. 焦点移动有没有做 1~2 帧预计算（而不是每帧 measure/layout）
  2. 列表有没有回收复用（RecyclerView 或手写 holder 池）
  3. 有没有在 onDraw 里 new Paint/new RectF/分配字符串（GC 抖动 = 掉帧）
  4. 播放器解码缓冲与 UI 是否同进程争 CPU（低端盒子常见）
- 语言层面 Java 与 Kotlin 编译后都是 dex，运行时没有区别。**全 Java 完全能做出来，只是代码量比 Kotlin 多 20~30%（主要是样板）。**

## 播放内核对比（低性能 TV 盒子，ARM32/1GB RAM 场景）

| 方案 | 语言 | 体积增量 | HLS/直播 | 软解/容错 | 结论 |
|---|---|---|---|---|---|
| Media3 ExoPlayer (media3-exoplayer-hls) | Java 壳 | +~1.6MB dex | 强（切片切换、ABR、重连） | 中等，可断言 | **主线推荐** |
| android.media.MediaPlayer | 平台 Java | 0 | 弱（HLS 版本碎片化） | 差 | 仅作兜底 |
| IJKPlayer (B站 ffmpeg) | C 库 | +8~14MB so | 强 | 强 | 老盒子兼容性最好，但维护停滞 |
| VLC (LibVLC) | C 库 | +25MB | 最强 | 最强 | 太重，启动慢 |
| FFmpeg + ANativeWindow 自绘 | C | 自己写 | 自己写 | 自己写 | 不是“做个播放器”，是“做个解码器” |

**主线：Media3 + 可选 IJK 兜底（通过接口抽象，一行切换）。**

## 低性能设备的硬性红线（写代码前先认这 4 条）
1. **禁用 ConstraintLayout 嵌套超过 2 层**，TV 屏固定 1920x1080，直接用绝对尺寸 + FrameLayout/LinearLayout 最省 CPU。
2. **列表一律 RecyclerView + `setHasFixedSize(true)` + 关闭 item 动画（`ItemAnimator = null`）**，或直接手写 LinearLayoutManager 的字幕式滚动。低端机 RecyclerView 的 item 动画是最大掉帧源。
3. **不做实时模糊（RenderEffect / RenderScript / blur）**。低端 GPU 一开必掉到 20fps。用“半透明纯色 + 渐变”假模糊。
4. **所有 ImageView 用 1 个 Bitmap 池 + `setLayerType(NONE)`**，别用圆角 MaterialCardView（它会创建离屏 layer）。

## 焦点框架
TV 上 `requestFocus()` 手动管是能用的，但**方向键跨列跨行时焦点的落点不可控**。
低性能场景的最优解：**自己算焦点（FocusEngine）**，不用 Leanback。
- 每个可焦点 View 注册到 `FocusEngine`（记录行列索引）
- 按键 → 引擎从网格索引直接算出目标位置 → `requestFocus()` 一次
- 好处：一次按键零 layout 遍历，低端盒子 60fps 稳；体积省 800KB（不引 Leanback）
